# DevMind 总体架构设计

## 1. 设计目标

DevMind 第一阶段是单体 Spring Boot 应用，完成“文档上传 -> 文本解析 -> 向量入库 -> 相似度检索 -> RAG 问答”的最小闭环。

设计原则：

1. 先保证 MVP 能运行，再增加异步化和分布式能力。
2. 文档处理、检索、对话三个领域边界清晰。
3. 外部模型调用必须通过适配层，业务代码不能绑定具体厂商。
4. 文档和向量处理必须可追踪、可重试、可幂等。
5. AI 只生成回答和建议，不直接执行危险数据库操作。

## 2. MVP 逻辑架构

```text
Client
  |
  v
REST API
  |
  +-- DocumentService
  |     +-- FileStorage
  |     +-- DocumentParser
  |     +-- TextChunker
  |     +-- EmbeddingService
  |     +-- VectorStore
  |
  +-- ChatService
        +-- Retriever
        +-- PromptBuilder
        +-- ChatModel
        +-- ReferenceBuilder

PostgreSQL + pgvector
Redis（MVP 可暂不启用，保留扩展点）
```

## 3. 领域边界

### Document 领域

负责文件元数据、文档状态、文件内容解析和文本分块，不负责回答问题。

### Retrieval 领域

负责文本块向量化、向量存储、Top-K 相似度检索和元数据过滤，不负责决定最终回答内容。

### Chat 领域

负责问题接收、检索上下文拼接、Prompt 构造、模型调用和引用来源组装。

### Infrastructure 领域

负责 PostgreSQL、pgvector、Redis、文件存储和模型客户端配置。

## 4. 文档处理流程

```text
上传文件
  -> 校验扩展名、大小和 MIME 类型
  -> 计算 content_hash
  -> 判断是否重复
  -> 保存 document 元数据
  -> 状态变更为 PROCESSING
  -> 解析文件文本
  -> 按标题、段落和长度切分
  -> 批量调用 Embedding
  -> 保存 document_chunk 和向量
  -> 状态变更为 COMPLETED
```

失败时：

```text
任意步骤失败
  -> 记录 error_message
  -> 状态变更为 FAILED
  -> 保留文档记录
  -> 后续支持重新处理
```

## 5. 问答流程

```text
用户问题
  -> 校验知识库
  -> 生成问题向量
  -> pgvector 检索 Top-K 文本块
  -> 按相似度过滤低质量结果
  -> 组装文档上下文和引用信息
  -> 调用 ChatModel
  -> 保存会话消息
  -> 返回 answer + references
```

Prompt 必须要求模型：

- 优先依据提供的上下文回答；
- 上下文没有答案时明确说明；
- 不得伪造文档中不存在的结论；
- 回答尽量引用来源标题和段落。

## 6. MVP 不做的事情

- 不拆微服务；
- 不引入 MQ；
- 不做复杂 RBAC；
- 不自动执行 AI 生成的 SQL；
- 不做多模型智能路由；
- 不在内存中保存文档处理状态；
- 不把 API Key 写入配置文件并提交到 Git。

## 7. 后续演进

### 文档异步化

上传接口只负责落库和创建任务，后台任务负责解析和向量化。任务状态持久化，支持失败重试和超时扫描。

### 检索增强

在向量检索之外增加关键词检索、标题权重、元数据过滤和 Rerank，形成混合检索。

### 权限隔离

知识库绑定用户或团队，检索时必须把权限条件作为元数据过滤条件，不能只在前端隐藏列表。

### SQL 诊断

SQL 诊断模块复用 RAG 检索能力，但增加 EXPLAIN 解析、规则初筛和测试库验证，AI 不直接修改生产数据库。
