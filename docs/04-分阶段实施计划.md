# DevMind 分阶段实施计划

## 1. 执行规则

- 每个阶段都要能启动和验证；
- 先完成可运行闭环，再做抽象和扩展；
- 不在 MVP 阶段引入 MQ、微服务和复杂权限；
- 每完成一个阶段，保留可演示结果；
- 外部模型调用失败必须有明确错误，不允许静默吞异常。

## 2. 阶段一：项目骨架和基础设施

### 目标

启动 Spring Boot 服务，Docker 启动 PostgreSQL + pgvector + Redis，完成健康检查。

### 任务

1. 创建 Maven 项目；
2. 配置 Spring Boot、Spring AI、PostgreSQL、Flyway 或初始化 SQL；
3. 提供 `docker-compose.yml`；
4. 配置环境变量读取模型 API Key；
5. 增加 `/actuator/health`；
6. 完成基础异常处理和统一响应结构。

### 验收

```text
mvn spring-boot:run
Docker Compose 启动成功
/actuator/health 返回 UP
应用可以连接 PostgreSQL
```

## 3. 阶段二：知识库和文档元数据

### 目标

完成知识库、文档元数据和基础 CRUD。

### 任务

1. 创建 `knowledge_base` 表；
2. 创建 `document` 表；
3. 实现知识库创建和列表接口；
4. 实现文件上传；
5. 计算 SHA-256 内容哈希；
6. 实现同一知识库内重复文档判断；
7. 增加文件类型和大小校验。

### 验收

```text
能创建知识库
能上传 Markdown/PDF
重复上传能识别
不支持的文件类型会被拒绝
```

## 4. 阶段三：文本解析和分块

### 目标

把 Markdown/PDF 转换成有顺序和元数据的文本块。

### 任务

1. 抽象 `DocumentParser` 接口；
2. 实现 Markdown Parser；
3. 使用 Apache Tika 实现 PDF 解析；
4. 抽象 `TextChunker` 接口；
5. 按标题、段落和长度进行分块；
6. 保存 `chunk_index`、标题、页码等 metadata；
7. 文档状态从 UPLOADED 变更为 PROCESSING、COMPLETED 或 FAILED。

### 验收

```text
上传 Markdown 后可以查看文本块数量
PDF 能提取基本文本
分块顺序稳定
解析失败能记录 error_message
```

## 5. 阶段四：向量化和向量检索

### 目标

完成文本块 Embedding、pgvector 存储和 Top-K 检索。

### 任务

1. 配置 Embedding 模型；
2. 确认实际向量维度；
3. 创建 `document_chunk` 表；
4. 批量生成文本块向量；
5. 写入 PostgreSQL + pgvector；
6. 实现按知识库过滤的 Top-K 检索；
7. 返回相似度和文档元数据。

### 验收

```text
文本块可以生成向量
向量可以写入数据库
相似问题能召回相关文档
不同知识库之间不会互相召回
```

## 6. 阶段五：RAG 问答

### 目标

完成问题向量化、上下文拼接、模型调用、引用来源返回。

### 任务

1. 实现 ChatClient 配置；
2. 实现问题向量化；
3. 检索 Top-K 文本块；
4. 过滤过低相似度结果；
5. 构造 RAG Prompt；
6. 调用 ChatModel；
7. 保存会话和消息；
8. 返回答案和 references；
9. 模型失败时返回 MODEL_CALL_FAILED。

### 验收

```text
可以根据上传文档回答问题
回答包含引用来源
无相关文档时不会强行编造
模型调用失败有明确错误
```

## 7. 阶段六：MVP 稳定性

### 目标

让 MVP 具备基本的工程质量。

### 任务

1. 增加文档处理幂等；
2. 增加删除文档和向量清理；
3. 增加全局异常处理；
4. 增加关键日志和 traceId；
5. 增加接口参数校验；
6. 增加核心 Service 单元测试；
7. 增加 Docker Compose 启动说明；
8. 用 Postman 或 Apifox 完成完整链路验证。

## 8. 阶段七：异步文档处理

### 前置条件

阶段一至六已经稳定，MVP 可以完整演示。

### 任务

1. 增加 `document_task` 任务表；
2. 上传接口只创建任务；
3. 任务状态持久化；
4. 通过线程池或 MQ 执行解析任务；
5. 失败任务支持有限重试；
6. 定时扫描超时 PROCESSING 任务；
7. 保证同一文档不会重复向量化；
8. 增加任务耗时和失败率指标。

建议先使用线程池完成异步化，再根据吞吐和可靠性需求引入 RabbitMQ 或 RocketMQ，不要在没有验证业务量前直接增加 MQ。

## 9. 阶段八：检索和权限增强

### 检索增强

- 增加关键词检索；
- 增加标题和标签过滤；
- 增加混合检索；
- 增加结果去重；
- 增加 Rerank；
- 增加检索评估样本。

### 权限增强

- 用户、团队和知识库关联；
- 检索时强制附带权限过滤；
- 文档上传权限校验；
- 删除和重新处理权限校验；
- 审计日志。

## 10. 阶段九：SQL 智能诊断

### 目标

将 RAG 能力扩展到 MySQL 慢 SQL 诊断，不直接执行 AI 生成的修改语句。

### 任务

1. 接收 SQL 和数据源标识；
2. 获取表结构；
3. 在只读或测试数据库执行 EXPLAIN；
4. 结构化解析 type、key、rows、Extra 等字段；
5. 使用规则识别明显风险；
6. 检索 MySQL 优化知识；
7. AI 生成诊断、索引建议和改写建议；
8. 展示原始执行计划和建议依据；
9. 增加人工确认和测试库验证流程。

禁止：

- 直接连接生产数据库执行 DDL；
- 自动执行 AI 生成的 UPDATE/DELETE；
- 只根据 SQL 字符串而不看 EXPLAIN 就下结论。

## 11. 每阶段提交建议

```text
feat: 初始化 DevMind 项目骨架
feat: 完成知识库和文档上传
feat: 完成 Markdown 和 PDF 文本解析
feat: 接入 pgvector 文本向量检索
feat: 完成基础 RAG 问答和引用来源
fix: 完善文档处理幂等和异常处理
feat: 文档解析任务异步化
feat: 增加知识库权限隔离
feat: 增加 SQL 执行计划智能诊断
```

## 12. 当前不要做的事情

- 不要先做前端大屏；
- 不要先拆微服务；
- 不要先接入多个向量数据库；
- 不要先做复杂 Agent；
- 不要先做自动执行 SQL；
- 不要为了简历堆叠 Kafka、RocketMQ、ES、Milvus；
- 不要在没有评估样本时宣称检索准确率。
