## 我建议的下一步

### 第一步：阶段七，异步文档处理（已完成）

已完成内容：

- 上传接口马上返回，状态是 `UPLOADED`，并返回 `taskId`；
- 新增 `document_task` 任务表；
- 后台线程池处理文档；
- 失败自动重试；
- 定时扫描卡住的任务；
- 应用重启后自动恢复未完成任务；
- 增加任务状态查询接口；
- 删除后的文档可以重新上传。

已验证：

- 上传 67ms 返回，任务后台自动完成；
- 无效模型地址触发 3 次重试后进入 `FAILED`；
- 文档和任务都保留错误原因；
- 删除后的文档重新上传会创建新任务。

### 第二步：阶段八，检索增强和权限隔离（已完成）

已完成内容：

1. 增加用户表；
2. 知识库绑定用户；
3. 检索时强制按用户过滤；
4. 增加关键词检索；
5. 合并向量和关键词结果，形成混合检索；
6. 增加启发式 Rerank；
7. 上传、删除、问答操作增加权限校验；
8. 审计日志。

已验证：

- 用户 2 看不到用户 1 的知识库；
- 用户 2 上传到用户 1 的知识库返回 `FORBIDDEN`；
- 混合检索后相关结果分数从 `0.8887` 提升到 `0.9301`；
- 创建、上传、问答都写入审计日志。

### 第三步：阶段九，SQL 执行计划智能诊断（已完成）

已完成内容：

- 新增 `sql_diagnosis` 诊断记录表；
- 接收 SQL 后执行 EXPLAIN（mock 或测试库）；
- 规则识别深分页、全表扫描、filesort、临时表、SELECT *、左模糊等风险；
- 可选关联知识库检索 MySQL 优化资料；
- AI 生成诊断建议；
- 只允许 `SELECT` / `EXPLAIN`，DML/DDL 被拒绝；
- 支持查询诊断记录列表和详情；
- 写入审计日志。

已验证：

- 深分页 SQL 识别出 `HIGH` 风险并返回执行计划；
- `DELETE FROM orders` 被 `INVALID_ARGUMENT` 拦截；
- 诊断记录可查询，审计日志包含 `SQL_DIAGNOSIS`。

## 不建议现在做的事

- 不拆微服务；
- 不加 Kafka / RocketMQ / ES / Milvus；
- 不做复杂 Agent；
- 不做前端大屏；
- 不自动执行 SQL；
- 不在没有评估样本时宣称检索准确率。

## 最终建议

阶段七、阶段八、阶段九已经全部完成。后续可以考虑：

- 文档异步化接入 MQ 和分布式任务；
- 模型 Rerank 替换启发式排序；
- 多模型路由和 Token 成本统计；
- 前端管理界面；
- Docker Compose 一键部署和 CI/CD。

这些都属于增量优化，不再阻塞当前 MVP 演示。
