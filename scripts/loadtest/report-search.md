# DevMind 检索性能压测报告（优化前后对比）

## 结论

- 场景：**纯语义检索（KB=19，不调 LLM）**，`POST /api/knowledge-bases/19/search`
- 环境：mock 模型（embedding 1024 维）· 16 并发 · 30s · 成功率 **100%**
- 优化后：**QPS 167.8 → 183.1（+9%）**，**P50 94.0 → 86.1 ms（-12%）**，P95 128→119 ms
- 热请求（同问题二次命中）单发延迟 **~18 ms**（冷启动首次 ~136 ms，主要是一次性 embed + 缓存回填）
- 说明：多次运行机器噪声约 ±8%（本地 Windows + 每分钟定时工作流占资源），以上取较佳一次

## 优化前后对比

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| QPS | 167.8 | 183.1 | +9% |
| P50（ms） | 94.0 | 86.1 | -12% |
| P95（ms） | 128.1 | 119.2 | -7% |
| 成功率 | 100% | 100% | — |

## 优化内容

1. **Embedding 两级缓存（`CachedEmbeddingGateway`）**：
   - 新增 L1 进程内内存缓存（`ConcurrentHashMap`，上限 2000 条，超限整体清空）；
   - 高频同问题直接内存命中，跳过每次的 `embedding_cache` 表查询（每请求省 1 次 DB 往返）；
   - L2 仍为 `embedding_cache` 表（跨实例共享），写穿时同时回填 L1。
2. **Hikari 连接池 10 → 20**（`application.yml`，可通过 `DEVMIND_DB_MAX_POOL_SIZE` 覆盖）：
   - 单次检索链路约 5-6 条 SQL（权限检查 3-4 条 + 向量检索 + 关键词检索）；
   - 16 并发下 10 连接是明显竞争点，扩到 20 后连接排队显著缓解。

## 瓶颈定位（分析过程）

- 向量检索 SQL 实测 **1.27 ms**（EXPLAIN：851 行 Seq Scan + Hash Join，数据量小优化器弃用 HNSW 索引，非瓶颈）；
- 关键词检索 SQL 实测 **0.67 ms**；
- 单发热请求 18 ms ≈ 5-6 条 SQL 串行往返 + Java 侧处理；
- 并发下 P50 放大主要来自 **DB 往返次数多 + 连接池竞争**，而非单条 SQL 慢。

## 可选的进一步优化（未做，记录备查）

- 权限检查（KB 本体 / member / admin / team）加 TTL 缓存：每请求可再省 3-4 条 SQL；
  因缓存会破坏同 JVM 内"先授权后撤销"的越权测试时序，且多实例下有最长 TTL 的访问窗口，未引入。
